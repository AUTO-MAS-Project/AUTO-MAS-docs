# 导入与载荷视图

`MaaFW/tools/embedded/embedded_project.py` 负责把项目来源导入为载荷，再为每个托管生成运行视图。`MaaFW/tools/core/project_update/` 负责投影、载荷登记和文件复用。现有托管通过切换视图更新内容，项目路径与托管身份保持稳定。

## 导入

手动导入和运行前的补建都以托管的视图为操作对象。

- **定位项目根**：有效项目根只从一处取：`embedded_project.resolve_maafw_project_root` 永远返回视图，新代码不许再自行读取 `Info.Path`，避免多处各自读取导致副本与来源混用。
- **处理架构差异**：唯一例外是运行前架构自检——在副本自带原生库架构不符时，只读地检查一次来源目录，以决定提示「重新导入」还是「换发行包」（[#1024][1024]），给选错架构的用户一条可行的修正路径。
- **确定视图路径**：视图目录名取托管 UUID 去除连字符后的前 12 位，不写入配置且不可手改。因为 Python 字节码前缀树中项目根会出现两遍，过长的路径会触发 Windows 的 `MAX_PATH` 限制。
- **判断是否需要导入**：`ensure_embedded_copy` 在视图不存在，或 `Info.Path` 与导入报告中的来源不是同一目录时执行一次导入；若来源已删除而视图健康，则不做任何操作，兑现「来源目录可删除」的承诺。
- **重建缺失视图**：当视图与来源目录均不存在时，从同项目的其他托管或已登记的来源反查，按本托管渠道的最新版重建（`_rebuild_from_group`），同样确保来源删除后仍可恢复。
- **校验来源**：复制之前先校验来源目录（[#1258][1258]），避免先复制再写字段时触发 500 错误并导致副本与来源错位。
- **展示副本路径**：导入后目录字段锁定并仅显示副本路径；来源目录此后仅作记录，更换项目请新建托管。
- **报告导入进度**：导入进度按投影字节数经 WebSocket 推送，避免大项目导入时界面长时间无反馈。
- **识别托管类型**：导入后按项目本身决定托管类型（`flavor.decide_project_config_class`），支持双向自动切换且保持 UID 不变。

## 投影

| 规则                                                                                                                                                                                                                                                               | 为什么                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 白名单 = interface 声明的内容（import、resource、控制器附加资源、语言文件、agent / pretask 目录、依赖清单、图标、欢迎信息）+ **剩余不超过 64 MB 的未声明顶层条目**（`projection.UNDECLARED_KEEP_LIMIT`）                                                           | MaaEnd 的 `data/`、`locales/`，M9A 的 `data/activity` 都没在 interface 里声明，却是 agent 运行时要读的                       |
| 规则第 2 版：按名字剔除的只剩顶层的界面程序、Qt 运行时与顶层运行期目录（`cache/ logs/ temp/ update/ backup/` 等）；自带 Python、.NET 托管库、标准布局的原生库目录按**内容**确认后才剔；任意深度只剔无歧义的缓存与 `.pyc/.log/.tmp`（[#1104][1104]、[#1117][1117]） | 旧规则逐级按目录名剔，误删过某项目 agent 代码里的 `battle/runtime/` 与另一项目资源里的 `UI/` 图片                            |
| `debug/` 不按名字剔，也不进载荷；导入时从来源的 `debug/` 挑出不超过 1 MB 的非日志状态文件，作为视图私有文件（`_runtime_state_seed`）                                                                                                                               | 有的项目把会读回的持久状态（账号盐值、时区偏移）放在 `debug/`                                                                |
| 项目自带的原生库目录与解释器目录**原样带走**，分类规则在里面不起作用、只剔 `__pycache__`                                                                                                                                                                           | 有的 agent 要求特定 Python 版本，有的原生 agent 固定从 `<项目>/maafw` 加载；CPython 自带名叫 `build` 的子目录，剔了 pip 就坏 |
| 冻结 Python 外壳散在根目录的二进制依赖包不带                                                                                                                                                                                                                       | agent 的 `PYTHONPATH` 是项目根，半截的包会变成命名空间包盖住真正的模块                                                       |
| 不剔任何架构的文件；没有本机能用的那份时，在运行环境日志开头提示（[#1102][1102]）                                                                                                                                                                                  | 剔了就找不回；提示按当前视图现场计算，换版本不残留                                                                           |
| 检测到混装原生库（`maafw/` 与 `runtimes/<rid>/native` 并存）只提示、不删（[#1144][1144]）                                                                                                                                                                          | 清理放到全量更新时按新包判                                                                                                   |

## 载荷与视图

磁盘上的载荷和视图各自记录不同的信息。

- **载荷目录**：载荷存放在 `data/mfw/.payloads/<谱系>/<版本>-<hash8>/` 并附同名清单，内容不可变；视图位于 `data/mfw/<12hex>/`（[#973][973]）。这样可以做到一次下载、一次落地、一次预检；运行中的托管不受打扰；差量基线不会被 agent 热更新污染；复用时也不会带走运行期状态。
- **视图目录**：视图是**完整的硬链接目录树**，不做目录级 junction 拆分。Windows 没有 overlayfs，`data/`、`config/`、`python/` 都是出厂文件与运行期写入混放；agent 按工作目录或可执行文件位置解析路径，只有完整的目录树才不会产生行为差异。
- **载荷 ID**：载荷 ID 仅由版本号与文件内容哈希决定，确保同一棵目录树必然算出相同的 ID。
- **视图路径**：视图路径永不改变，因此环境缓存、隔离 venv、interface 缓存、备份和运行池对账都可以稳定地以路径为键。
- **视图标记**：视图标记 `.auto_mas_view.json` 是物化事实的唯一来源，不计入指纹，随目录原子换入。因为切换发生在工作线程而配置只在事件循环上修改，两者不能互相等待；标记先落入新目录才能避免出现「新内容 + 旧标记」。
- **配置字段**：谱系、载荷和版本都不写入 `ScriptConfig.json`，唯一新增的配置项是 `Embedded.FollowSource`，避免把内部簿记暴露给界面。

## 文件共用与写穿巡检

| 设计                                                                                                                                                                                                   | 为什么                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| 共用谓词只有一个 `projection.is_shared_path`：≥ 64 KB、不在 `config/ debug/ logs/ temp/ cache/ .pycache/` 下、后缀不是 `.lock .sha256 .pth .log .tmp`、不在 `*.dist-info` 里、不在谱系记下的私有路径里 | 运行期会被原地改写的文件都在 64 KB 以下或这些目录里  |
| 满足的存进 `data/maafw_blobs/<ab>/<sha256>`，载荷与视图里是 NTFS 硬链接；链接失败退回复制                                                                                                              | 同样的字节只存一份                                   |
| 通过 `blob_store.place_fresh` 独占新建写入共用文件；小文件不入库；链接失败退回复制                                                                                                                     | 硬链接没有写时复制，写穿会改坏所有视图               |
| 不用只读属性保护                                                                                                                                                                                       | 只读属性跨链接共享，会让删除、替换、pip 卸载全部失败 |
| 每次运行收尾做写穿巡检（`view_audit.py`）：链接数 > 1 且修改时间晚于物化时刻才读哈希；确认写穿就隔离该文件、记为私有路径、把载荷标成损坏（下次更新只要全量包）                                         | 修改时间只作触发、哈希作确认，扫描几乎不花时间       |

## 谱系与组

| 设计                                                                                                                                                     | 为什么                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 谱系键 = `mirrorchyan_rid` > `github` > `name`（取原文值）                                                                                               | 更新发现本来就以 Mirror 酱资源 id 为入口           |
| 组 = 谱系 + `Update.Channel`；每个渠道的最新版**只前进、同版本不换 id**                                                                                  | 同组永远同一个载荷；两个来源导入同一版本不会来回切 |
| 同版本换 id 只有两个例外：组的最新版自带的 MaaFramework 在本机加载不了而新登记的能加载（[#1024][1024]）；新登记的按更高版本的投影规则建（[#1117][1117]） | 修复已经装坏的载荷                                 |
| 自动更新模式只决定谁去联网发现：运行前更新会推进整组，旧 `AfterRun` 配置也按运行前执行；「不更新」的托管自己不查，但组推进时照样跟着切                   | 没有钉住                                           |
| 改渠道 = 换组，下次运行前切到新渠道的最新版，**允许降级**；新渠道还没有版本就留在原版本                                                                  | 同一项目要停在两个版本，唯一办法是两个渠道         |
| 本地导入：比组新 → 整组推进；相同或更旧 → 不登记，托管立即用组的当前版本                                                                                 | 组里容不下领先或落后的成员                         |
| 远端渠道回滚不跟随                                                                                                                                       | 最新版只前进                                       |

## 切换视图

切换由 `embedded_project.switch_view()` 承担。升级、渠道切换及投影补齐共用该入口。

- **物化新视图**：`embedded_project.switch_view` 在暂存目录按新载荷重建链接树 → 带上视图私有文件 → 本地改过的受管文件以新版本为准，旧内容留档到 `data/maafw_project_state/<视图哈希>/local-modified/` → 标记先写入暂存目录 → 通过两次目录重命名换入。过程声明式、幂等、与升级或降级方向无关，约耗时 2 秒。
- **恢复未完成的切换**：切换日志存放在 `data/mfw/.switch/`，启动时 `recover_switches` 按磁盘状态收尾，不会「重跑切换」，避免半途崩溃后重跑把整棵新树误判为本地修改。
- **保留运行状态**：旧视图私有、新载荷中也存在的路径以载荷为准；例外是 `contracts.RUNTIME_STATE_FILES`（如 M9A 的账号记录）会原样带过去，避免换版本把账号记录回退到导入那天。
- **处理版本相关状态**：例外中的例外是 `contracts.VERSION_BOUND_STATE_FILES`（M9A 的热更新缓存），换到另一个载荷时只取新载荷那份。因为缓存与随版本发布的数据表成对，保留旧缓存会导致热更新一直被跳过。
- **使用新版解释器**：自带解释器里的 `maafw` binding 不视作受管文件，而是以新载荷为准、不留档也不作为私有文件带走（`_is_maafw_binding_path`），因为它是准备环境时固定回去的，而非用户修改。
- **补齐缺失文件**：当新载荷是旧载荷的超集且共同文件内容相同时（由投影补齐生成），只补齐缺失文件，视图已有文件原样保留，避免项目因补齐而重跑热更新。
- **确认运行环境**：切换之后无条件接一次运行环境确认；确认成功才在标记里记下「已为这个载荷确认过」，防止隔离 venv 的分钟级重建拖进运行期，让用户误以为任务卡住。

## 复用已导入项目

| 设计                                                                                                                | 为什么                                         |
| ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 入口只在**新建托管对话框**：第一行「选择本地目录」，下面列出已导入的项目，只列与所选类型相同的项目                  | 复用是新建阶段的决定；导入后的目录字段只是展示 |
| `embedded_project.clone_embedded_copy` 从源托管挂的**载荷**物化新视图，不读源视图、不要求源空闲、不带源的运行期状态 | 载荷不可变                                     |
| `Info.Path` 与导入记录随源一起继承；类型随项目                                                                      | 运行前检查靠两者比对决定是否重导               |
| 「复制托管」复用同一个函数                                                                                          | 一种操作一份实现                               |

## 开发者模式

`Embedded.FollowSource`，默认关（[#1294][1294]）。给在本地发行包或源码仓里改东西修 bug 的开发者用。

| 行为                                                                                                                                       | 为什么                             |
| ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------- |
| 组换成私有渠道 `dev:<视图名>`（`effective_channel`），每次导入都前进；载荷版本带 PEP 440 本地段 `+dev`                                     | 同项目的其他托管与官方更新碰不到它 |
| 运行前检查按投影白名单算来源签名（路径 + 大小 + 修改时间，≤ 1 MB 的再加内容哈希），变了就重导；内容没变不重建视图                          | 避免每次全量复制                   |
| 读不了来源（文件被锁、interface 暂时不在、解析失败）时**沿用上次同步的版本**照常运行，日志写一行醒目警告；只有视图本身不在才按导入失败处理 | 开发者的来源目录经常处在半成品状态 |
| 「立即同步」不看签名、强制重导；运行中、更新中、来源不在都直接拒绝                                                                         | 补上修改时间没变而漏掉的改动       |
| 不参与项目更新：自动更新跳过，手动检查与更新被拒                                                                                           | 以来源目录为准                     |
| 离开开发者载荷时不留「本地改过」档                                                                                                         | 那些差异就是从来源同步来的         |
| 关掉开关回到原渠道组的最新版；复制、复用不继承开关，源挂开发者载荷时新托管取原渠道的正式版本                                               | 开发者载荷不扩散                   |
| 开发者载荷不传播到普通渠道                                                                                                                 | 同上                               |

## 源码形态

源码仓式的项目：`assets/interface.json`，agent 写成 `"child_exec": "python", "child_args": ["-u", "./../agent/main.py"]`，根上有 `agent/`、`requirements.txt`，没有 `python/` 与 `maafw/`（[#1294][1294]）。

| 设计                                                                                                                            | 为什么                                                                            |
| ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 视图按发行包的平铺布局建：`assets/` 提升到根，`agent/`、`requirements.txt` 等原样放根                                           | 与项目自己打包得到的布局一致                                                      |
| interface **不改写**：越出项目根的 agent 入口由 `interface/agent_entry.py` 的 `flattened_entry_path` 兜底，投影与解释器规划共用 | 一处兜底全对；改写就要在每份载荷里维护一份与来源不同的文件                        |
| 只放行有运行时映射的越界（agent 的第一个 Python 入口）；其他越界写法导入时就拒绝并说明                                          | 不让用户导入成功却在运行时报路径越界                                              |
| `child_exec: uv` 不支持（`describe_uv_agent`）                                                                                  | uv 按项目自己的锁文件另建环境，maafw 未必与运行用的 MaaFramework 同版本           |
| 源码形态一律处在开发者模式，界面上开关锁在开着                                                                                  | 没有正式发行渠道                                                                  |
| 被 CFA（MFW-PyQt6）源码热更新过的发行包目录走同一个入口兜底，不在导入时改写 interface                                           | 那正是 CFA 自己的解析规则；第一次走 MAS 更新后自然变成发行包写法（[#1157][1157]） |

## 迁移与回收

| 设计                                                                                                           | 为什么                                             |
| -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 启动期的一次性迁移在后台任务里跑，不挡主定时器                                                                 | 挡住主定时器会让按分钟匹配的定时任务被静默跳过     |
| 采纳旧副本时载荷内容以视图自身为准                                                                             | 「来源旧、视图新」会登记出残缺载荷                 |
| 全部采纳完再统一定同版本的最新版，再把每组统一过去；迁移统一不单独预检                                         | 结果与托管顺序无关；目标载荷来自本机跑过的健康副本 |
| 回收只在启动期做：删掉无人引用的载荷；一个视图都不剩的项目整个收走；本进程启动之后建的不收；删前在谱系锁内复判 | 有引用就留、无引用就删，不做「保留最近 N 版」      |
| 随后删掉链接数为 1 的共用文件；更新包下载缓存 7 天没用的删掉                                                   | 同上                                               |
| 数据备份排除 `data/mfw`、`data/maafw_blobs`、`data/maafw_update_cache`                                         | 都能重建，硬链接按路径读会重复打包                 |

## 限制

- 开发者模式下大于 1 MB 的文件只比大小与修改时间；源码形态会把源码仓里不超过 64 MB 的杂项（测试、文档）一起带进视图。
- 没有界面入口可以「用本地新版本更新现有托管」，只能新建托管导入（比组新会推进整组）。

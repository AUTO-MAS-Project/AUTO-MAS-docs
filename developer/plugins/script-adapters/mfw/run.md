# 运行

`MaaFW/tools/embedded/runner_task.py` 负责把账号任务快照转换为运行计划，处理设备准备、重试和收尾。`MaaFW/tools/core/runner/` 中的 worker 按计划运行项目并回传每项任务的结果。

## 任务快照

账号的 `Task.TaskSnapshot` 是保存任务队列及选项的 JSON 字符串。下面展示解析后的对象结构。

```json
{
  "taskOrder": ["<任务实例 ID>"],
  "taskChecked": { "<任务实例 ID>": true },
  "taskOptions": { "<任务实例 ID>": { "<选项名>": "<选项值>" } },
  "globalOptions": { "<全局选项名>": "<全局选项值>" },
  "taskLabels": { "<任务实例 ID>": "<自定义显示名>" }
}
```

- **队列与选择**
  - `taskOrder`：任务实例 ID 的执行顺序。
  - `taskChecked`：各实例是否勾选。
  - `taskLabels`：可选。每个实例的自定义显示名。
- **选项值**
  - `taskOptions`：以任务实例 ID 为键保存该实例的选项。
  - `globalOptions`：一个账号的全局选项，见[全局选项](#全局选项)。

| 设计                                                                                                                                                          | 为什么                                                           |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 队列元素是**实例 id**：第一份沿用任务名，之后是 `<任务名>__MAS_DUP__<随机后缀>`；解析时先查整串是不是合法任务名（[#660][660]）                                | 同一任务可重复入队、旧配置零迁移；任务名本身带分隔符也不误判     |
| MFAA 私有扩展 `repeatable + repeat_count` 与任务表里的同名任务，都展开成重复实例（上限 99），不做 runner 内循环（[#973][973]）                                | 失败按 MAS 规则继续下一份                                        |
| 「每日 / 每周 / 每月仅一次」按任务名记，同一轮内也只安排一次（`runner_task._filter_period_once_tasks`）                                                       | 先跑的那份成功会把整个任务名记成完成，同轮还没跑的副本会被误跳过 |
| 显示名 `taskLabels` 只存在那一份实例上，不改任务名；运行与项目更新仍按实例 id 匹配，运行日志仍用 interface 的 label（[#1301][1301]）                          | 显示名只影响界面                                                 |
| 快照为空时按 `Task.SelectedPreset` 套项目预设；套模板、导入其他账号队列时把它写空（[#1260][1260]）                                                            | 避免空快照误套预设                                               |
| 保存的选项值对不上当前 interface（项目改了 case 名）时退回默认，并在运行日志开头的「运行计划提示」里各列一句（`run_plan.describe_stale_option_values`）       | 不静默                                                           |
| interface 里已经没有的任务：队列里留成虚影；运行时记跳过并写进运行总览；有失效任务时照常算完成，但报告标出「有失效任务」并算进汇总的未完成数（[#1147][1147]） | 改名后旧任务曾静默消失，一编辑就永久丢失                         |

## 全局选项

| 设计                                                                                                                           | 为什么                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| `global_option`（连同 case 下挂的子选项）每个账号只存一份，在 `globalOptions`；账号页在队列上方只显示一次（[#1294][1294]）     | PI 语义就是全局的                                                          |
| 同一选项也被任务 / 资源 / 控制器引用时，它按任务存值、任务的值生效；只有「只属于全局」的选项，任务上的值不生效                 | 与 PI 示例的结果一致                                                       |
| 判「只属于全局」要用**不按当前资源 / 控制器过滤**的选项表                                                                      | 否则一个还被未选中资源引用的全局选项会被误判，盖掉账号的全局值             |
| 风味走 `task_ids` 建计划时必须把 `global_options` 一并传给 `build_plan`                                                        | 漏传不报错，全局选项会静默回到默认值                                       |
| 旧配置迁移：全局表里缺或坏的项，取队列里第一个勾选的、带合法值的实例；前后端同一口径                                           | 升级不丢值                                                                 |
| **降级兼容双写**：保存时把只属于全局的值抄到每个任务实例上（`task_config.mirror_global_options_to_tasks`），新版本不读这些副本 | 旧版本运行期按任务读；旧版本保存会丢掉 `globalOptions`，升级回来靠副本找回 |
| 从同托管其他账号导入队列不带全局选项                                                                                           | 导入只换队列                                                               |

资源组、控制器组里的选项与任务选项一样**按任务各存一份**，与 MXU 一致。

## 预设、自定义模板与导入

| 设计                                                                                                             | 为什么                         |
| ---------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| 「应用预设」直接替换队列，不再确认                                                                               | 预设的既有语义                 |
| 自定义模板存在托管级 `Task.Templates`，同托管的账号共用，风味子类自动继承，不写进项目目录（[#1260][1260]）       | 模板属于 MAS 配置，不属于项目  |
| 存模板时去掉虚影、受管任务与**密码值**；同名不覆盖；失效的模板照常显示并标出数量，全部失效时「应用」置灰但仍可删 | 密文不跨账号；模板不该静默消失 |
| 从同托管其他账号导入：覆盖当前队列，当前的前置任务留在最前，失效与受管任务跳过，密码值不带                       | 同上                           |
| 运行器只读快照，不读 `Task.Templates`                                                                            | 模板只是快照的一种来源         |

## 运行计划

`build_maafw_run_plan()` 将已选任务和选项解析为 worker 执行的数据。

- **解析任务选项**：`run_plan.build_maafw_run_plan` 产出每个任务的 pipeline override；`run_plan.resolve_run_selection` 是选控制器与资源的唯一口径（托管资源留空时按控制器回落）。 运行期、保存钩子与风味整理三处要一致。
- **合并覆盖**：`pipeline_override.deep_merge_pipeline_override`：子键逐层合并，数组与标量后者覆盖前者。 深合并不丢作者分头写的字段，与 CFA 一致；**不要为了与 MFAA / MXU 一致改成整体替换**。
- **读取选项默认值**：select 的私有 `default` 故意不认。 作者自己的 MXU / MFAA 外壳都不认，认了反而比作者更激进。
- **解析字符串输入**：字符串输入留空时默认使用项目接口的 `default`。风味可通过 `no_default_fallback_inputs` 声明需下发空字符串的字段。 项目默认值由项目提供，风味仅补充其特有字段的语义。
- **解析数字与布尔值**：数字 / 布尔输入没填或填错：跳过这个选项的覆盖并告警，不让整轮失败。 发行包的小毛病能降级就降级。
- **检查多选数量**：checkbox 的 `min_count / max_count` 不满足时报错（`MaaFWCheckboxCountError`），不静默截断。
- **加载项目接口**：加载器容错：缺 import 文件、`scan_dir` 不在、缺 `interface_version`（按 2 处理）都只告警，告警进运行日志开头与导入报告。 interface 由别的客户端写出，读不出来就是整个项目用不了。
- **确定 agent 连接时限**：`agent.timeout`（秒）只决定等 agent 连上的预算（不写或 -1 为 10 分钟），连上之后不限时；写死的 `agent.identifier` 运行时拼上实例后缀，纯数字（端口）原样用。 与 PI 语义一致；多开不撞名。

## 启动 worker 并收集结果

宿主把计划写入 job 文件，worker 按同一版本的契约读取。

1. **启动 worker**：worker 以 `python -m` 启动，工作目录是应用根，并设 `PYTHONSAFEPATH=1`。 受监督布局下应用根还有一棵随安装包带来的旧源码，不设会导入旧代码。
2. **保持协议一致**：job 文件新增字段要求宿主与 worker 同版本；旧 worker 遇到不认识的字段会静默忽略。 混跑时优雅退化。
3. **回传任务结果**：worker 每完成一个任务就上报一次，宿主累计；周期任务的完成标记放在收尾的 `finally` 里。 超时、取消、崩溃都不丢进度。
4. **初始化控制器**：连上控制器后先截一张图（`runner._prime_first_screencap`），每次连接一次，失败只记日志（[#1029][1029]）。 控制器没截过图时 `cached_image` 会抛错、`resolution` 是 (0, 0)，有的项目在第一个任务开始时就读它们并停掉自己；MFAAvalonia 也这样做。
5. **保存账号状态**：托管持有配置锁，账号的运行状态通过持票上下文提交，最终由宿主保存并解锁。 运行中可稳定更新当前条目，收尾统一释放配置锁。
6. **回传线程日志**：在工作线程里跑的钩子与回调写日志，一律经 `loop.call_soon_threadsafe` 转回事件循环。 直接写会抛「no running event loop」，又被容错吞成一句「失败继续」。

## 时限

时限适用于账号整次运行或单项任务。原地打转另有检测规则。

- **账号整次运行**：`Run.RunTimeLimit`（MFW 默认 120 分钟）是套在单个账号整次运行上的**硬超时**，与其他专项的「日志停滞超时」同名不同义。 MFW 里有没有日志与卡没卡住无关：卡住时照样刷日志，正常时长动作可以很久不出声。
- **下发截止时刻**：截止时刻随 job 下发，worker 到点自己停下当前任务、截一张超时图，带着已完成的任务正常回传；宿主只在其后加一段宽限兜底，worker 没停下才强杀（[#880][880]）。 以前强杀既没截图也没进度。
- **单任务时限**：`Run.TaskTimeLimit`（默认 45 分钟，0 表示不限）与按任务名覆盖的 `Run.TaskTimeLimitOverrides`；风味可用类属性 `DEFAULT_TASK_TIME_LIMIT_OVERRIDES` 内置几条（[#1180][1180]）。 一个卡住的任务不该吃掉整轮。
- **处理任务超时**：单任务超时只停那一个、截图：计划里第一个任务或风味的关键任务超时就结束本轮，其余记一条失败后继续；**继续之前先等停止真正生效**（上限 60 秒）（[#1296][1296]）。 `post_stop` 后当前任务还要跑完手上的节点，这期间新投的任务会被框架拒掉。
- **判断超时与强停**：「本任务超时」的判断必须放在「脚本侧强停」判断之前。 我们自己的 `post_stop` 也会让 tasker 进入停止状态，顺序反了会被当成脚本侧强停，跳过本轮剩余任务。
- **转换时限单位**：分钟到秒的换算只有一处 `runner_task.task_time_limits_from_config`，宿主算好随 job 下发。 worker 是独立进程，读不到配置。

## 重试

| 设计                                                                                                                                                                    | 为什么                                                       |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 任一轮失败（不只超时）且还有下一轮：关掉**由 MAS 启动的**游戏 / 模拟器，下一轮重新启动；不是 MAS 启动的不碰；关模拟器时清掉缓存的连接信息（[#880][880]、[#1028][1028]） | 接回同一个卡住的窗口只会白等；模拟器重开后旧的进程号已经失效 |
| `Run.RunTimesLimit` 新建默认 3                                                                                                                                          | 脚本自己的加载超时偶尔抖一次就整轮失败                       |
| 非周期任务**默认全部重跑**；风味可用 `skip_on_retry_entries` 显式列出「重跑纯属浪费」的任务，没列的照旧补跑（[#1296][1296]）                                            | 启动类任务在游戏崩溃后必须重跑，只有作者知道哪些可以不重跑   |
| 每次尝试单独一份日志；新一次尝试开头写「上一次（第 N 次）：原因」，确实关过客户端才补「已重启游戏/模拟器」（[#1011][1011]、[#1295][1295]）                              | 否则失败原因被新日志冲掉，用户只看到莫名其妙的重试           |
| 架构不符、运行环境不可用、信号、需要更新客户端等不重试                                                                                                                  | 每次都一样，重试只会多起停一次模拟器                         |
| 任务前 / 后脚本每个账号各跑一次（[#638][638]）                                                                                                                          | 重试三次各跑三遍不对                                         |

## 关键任务、收尾任务、不可选任务

由风味声明，契约写在 `MaaFW/tools/embedded/flavor.py` 的模块说明里，详见 [风味](./flavor.md)。

| 声明                                 | 效果                                                                                                                                                     |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `abort_round_entries`（关键任务）    | 失败或单任务超时即结束本轮，照常重试                                                                                                                     |
| `nonfatal_entries`（收尾任务）       | 失败、超时、打转、被脚本侧强停都只截图记一行，不算本轮失败、不重试；优先于「第一个任务超时就结束本轮」。用户停止、整轮时限、信号、游戏没能启动先于它处理 |
| `unselectable_entries`（不可选任务） | 预览返回 `unselectableReason`；账号页不让选，已在队列里的照常显示可删；运行时在风味装饰之前剔掉并记一行，因此上面两种声明对它不起作用                    |

## PC 游戏启停

`Game.LaunchMode` 决定 Win32 控制下怎样取得游戏窗口。启动、重试和最终收尾由 `runner_task.py` 编排。

- `<启动方式>`
  - `DirectExe`：默认值。MAS 使用 `Game.LaunchPath` 和启动参数打开游戏，收尾时关闭本次打开的游戏。
  - `URL`：MAS 打开 `Game.URL`。同时配置 `Game.LaunchPath`，用于识别窗口与进程。
  - `AttachOnly`：接管由项目、用户或其他方式启动的游戏窗口，最终按 `Game.CloseMode` 处理进程。
- `<接管窗口后的关闭方式>`
  - `Script`：由项目负责关闭。
  - `OnFailure`：默认值。未正常完成时关闭本次运行中新出现的匹配进程。
  - `Always`：最终收尾时关闭本次运行中新出现的匹配进程。

1. **准备游戏窗口**：`DirectExe` 和 `URL` 发现游戏已在运行时复用窗口。Unity 分辨率覆盖在这两种模式下生效，由 `game_resolution.py` 修改 Unity 播放器设置。等待时间以 `Game.WaitTime` 为基础，URL 模式允许更长的启动等待。
2. **执行项目的运行前设置**：项目接口中的 `pretask` 随首次尝试执行。已成功时，重试根据客户端是否仍在决定是否重跑。账号级的脚本前后任务各执行一次。
3. **收尾设备**：`DirectExe` 和 `URL` 只关闭由本次运行启动的进程。`AttachOnly` 的关闭规则只在最终收尾执行，并保留运行前已存在或无法确认启动时间的进程。ADB 控制下，模拟器启动时可使用选定包名启动游戏。

| history 里的 `.maafw.log` 是原生日志本次运行部分的按字节原样副本；MAS 自己的输出另存 `.worker.log`；项目 agent 自写的日志另存 `.project.log`（[#881][881]、[#1117][1117]） | 可以原样转交脚本作者                                                                      |
| `maa_option.json` 里 `logging` 写 `true`                                                                                                                                   | 这是上游默认；MaaFramework 没有文件日志级别，只有开和关                                   |
| PI `password: true` 的输入值在快照里是带 `mas-dpapi:` 前缀的密文；MAS 自己的日志出口对长度不少于 4 的密码打码，更短的**不打码**                                            | 一两个字符全局替换会让整份日志没法看；框架自己写的 `debug/maafw.log` 里是原文，MAS 管不了 |
| 带 `[MaaFW 详情]` 前缀的行只进 `.worker.log` 与后端日志，界面只给结论                                                                                                      | 新增日志出口也要拦                                                                        |
| 子进程输出进日志一律按**结尾**截                                                                                                                                           | 截开头会正好丢掉异常那一行                                                                |
| 资源 hash 不一致只进详情日志（[#1151][1151]）                                                                                                                              | 用户没法处理                                                                              |
